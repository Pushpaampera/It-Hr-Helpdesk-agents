## Agent graph and handoffs
```
guard -> supervisor -> (it_support | hr_policy | other_reply)
                           -> action (only if needs_action)
                           -> ticketing (only if unresolved/escalated)
                           -> feedback
```
- **guard** runs first on every turn: rule-based checks (no LLM) for requests to another
  person's personal/payroll data and prompt-injection patterns. Blocks and logs to `audit_log`
  before any other agent sees the message.
- **supervisor** (Sage) returns strict JSON `{route, confidence, needs_action, intent}`. Routes
  to `OTHER` and asks a clarifying question if `confidence < 0.55`.
- **it_support** (Iris) / **hr_policy** (Hana) retrieve from `kb_chunks` via the bandit-selected
  strategy, answer with cited sources, set `unresolved=true` if the retrieved text doesn't
  support an answer.
- **action** (Atlas) only runs if `needs_action`. Tool calls: `reset_password`,
  `request_access` (pauses the graph via a LangGraph interrupt pending manager approval),
  `apply_leave`, `get_leave_balance`, `unlock_account`.
- **ticketing** (Tess) only runs if unresolved/escalated/user asked for a human.
- **feedback** (Finn) always runs last: emits `feedback_requested`, and on the user's rating,
  computes the LinUCB reward and updates `bandit_state`.

Full state is persisted step by step to `agent_events` (ordered by `seq` within a `run_id`).

## SSE event schema
`POST /api/chat/stream` returns Server-Sent Events. Event envelope:
```json
{
  "run_id": "uuid",
  "seq": 3,
  "type": "agent_event",
  "agent": "it_support",
  "status": "retrieving",
  "action": "hybrid_search",
  "caption": "Iris is checking the IT runbooks for VPN error 619.",
  "detail": {"strategy": "hybrid_rerank", "top_chunks": [{"id": "...", "title": "VPN Error 619", "score": 0.91}]},
  "model": "gemini-flash-lite",
  "latency_ms": 420,
  "tokens_in": 512,
  "tokens_out": 0,
  "ts": "2026-11-03T12:00:00Z"
}
```
Other event `type`s: `token` (streamed answer text), `handoff` (`from`, `to`, `reason`),
`approval_required`, `final` (answer, sources, route, resolved flag), `error`.

`status` values for `agent_event`: `started | working | tool_call | retrieving | completed |
handoff | error` (matches the `agent_events.status` CHECK constraint in
`docs/02_DATABASE.md`).

Every event also carries a plain-English `caption`, generated by server-side templates (no
extra LLM call) — see section 0.7 of the master prompt / `docs/phases/PHASE_10B.md` once built.

## Request lifecycle (implemented and verified in Phase 3 — see docs/phases/PHASE_03.md)
1. Frontend `POST /api/chat/stream` with the user's message (`user_id` in the body in Phase 3;
   Phase 4 switches this to the JWT-authenticated identity).
2. Backend (`app/agents/graph.py::start_chat`) creates an `agent_runs` row, builds a fresh
   `StateGraph` closing over a per-run `EventSink`, and calls `graph.ainvoke(...)`. Each node
   emits `agent_event`s as it starts/works/completes, persisted to `agent_events` *and* pushed
   onto an `asyncio.Queue` that the SSE endpoint streams from live.
3. On `request_access`, the `action` node creates a pending `approvals` row (via
   `app/mock_apis/it_system.py::request_access`), emits an `approval_required` event, then
   raises `langgraph.errors.NodeInterrupt`. `start_chat` detects the pause by checking
   `graph.get_state(config).next` (LangGraph returns normally from `ainvoke` either way — it
   does not raise to the caller) and sets `agent_runs.status = 'awaiting_approval'`. The SSE
   connection is deliberately left open (no closing sentinel) rather than closed.
4. A manager decides via `POST /api/approvals/{id}/decide`. The approvals router updates the
   `approvals`/`access_requests` rows and fires `app/agents/graph.py::resume_after_approval` as
   a background task, which calls `graph.update_state(config, {"approved": ...})` then
   `graph.ainvoke(None, config)` — reusing the *same* live queue (looked up by `run_id` in
   `events.py`'s `_LIVE_QUEUES` registry) so the original SSE connection keeps streaming new
   events in real time. The re-invoked `action` node is idempotent: it checks for an existing
   `approvals` row tied to the run before creating a new one.
5. A `final` event carries the answer, sources, route and resolved flag; the frontend then shows
   the feedback widget, which posts to `POST /api/feedback` (handled by `app/agents/feedback.py`,
   which updates the LinUCB bandit).
6. `GET /api/runs/{id}/events` replays a past run's full event list for the Replay control.
7. `GET /api/agents/live` (not yet built — planned for the Phase 10 Agent Control Room) will be
   a separate, always-on SSE stream aggregating all users' activity (anonymised for non-admins).

Pause/resume relies on a **module-level singleton `MemorySaver`** checkpointer (in-memory, not
persisted to disk) — acceptable for a local demo since the backend process doesn't restart
between a pause and its resume, but it means a server restart loses any run that's mid-approval.
See `docs/06_DECISIONS.md`.

## Frontend ↔ event mapping
See `docs/04_FRONTEND.md` (populated from Phase 5 onward) for which 3D component reacts to which
event type. In short: `handoff` events drive `DataPulse` beams between `AgentOrb`s, `retrieving`
drives `KnowledgeCore` chunk highlight + beam-back, `tool_call` drives the Action Agent's tool
card, `approval_required` drives the approval banner/card, `final` + a 1/5 star rating drives the
`Feedback` burst.
